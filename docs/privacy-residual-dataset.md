# Residual dataset statement (cf#223 stage 1 deliverable)

**What this is.** Conrad authorized the log scrub (stage 1) conditioned on a guaranteed end-user
privacy outcome, and required, before any stage-2 enable-flip is considered, a field-by-field
statement of **exactly what would be ingested if Workers observability were turned on for a tenant
studio, AFTER the scrub**. This is that statement.

**What this is not.** It is not a recommendation to enable anything. Nothing here proposes a flip.
Enabling observability on a tenant script remains gated on Conrad's explicit word (2026-07-19
ruling), and this document exists so that word is given against facts rather than against a summary.

Method and field list follow `vivijure-control-plane/docs/tenant-telemetry.md` (the audit that
produced the original disposition), so the two can be read against each other line by line.

---

## 1. What changed in stage 1

The audit named four leaking call sites and one leaking throw. All five are closed:

| Audit finding | State after the scrub |
|---|---|
| `render.bookkeeping_deferred` logged `project`, the user-chosen project NAME | logs `project_label` (a stable, content-free label); the name is gone |
| `console.error("router error", url.pathname, e)` | logs the matched ROUTE TEMPLATE (`/api/artifact/*key`), never the pathname |
| `cast-bundle.ts` logged R2 keys, artifact paths, bundle `voice_id` | key LABELS, and an `untrustedLabel` for a value an uploaded manifest controls |
| `openai-image.ts` interpolated the provider MESSAGE into a throw (a moderation refusal quotes the prompt back) | the enumerated `code`/`type` only; the prose is dropped |
| the same set on the self-host panel, plus the notify-email stub printing recipient, subject and body | same scrub; the stub is content-free by default with an operator opt-in |

Held by `tests/log-scrub.test.ts` on both panels: sentinels that cannot arrive by another route, a
control proving the harness sees them, and both negatives watched failing with the scrub disarmed.

## 3. The residuals in `Logs` and `Exceptions`, stated plainly

### 3.1 Error message text is still interpolated into log lines

Two log lines (`render.bookkeeping_deferred`, `router.error`) carry `reason: e.message`, and an
exception message is only as content-free as the throw site that produced it. That is a property of
the whole tree, not of these two lines, so it was censused rather than assumed:

- **vivijure-cf `src/`**: exactly ONE throw interpolated upstream text (`providers/openai-image.ts`).
  Closed in stage 1. No other throw in the studio source carries a fetched body.
- **`vivijure-core`**: no throw interpolates a fetched body. It does, however, put upstream text into
  RETURNED error strings in four places (`runpod-submit` slices 300 chars of a non-JSON RunPod
  response; `render-mux` and `beat-analyze` slice 200 chars of an error body; `renders-db` /
  `cast-db` persist a 2000-char error into D1). Those land in job rows and API responses. They reach
  a LOG line only if a caller throws one of them out through the router, which nothing does today.

**Honest characterisation:** `Logs` and `Exceptions` are content-free at every call site the studio
authors, and the remaining exposure is second-order, through upstream error prose that our own
backend or a provider generates. It is small, it is enumerated above, and it is not provably zero.
Anyone treating "post-scrub Logs are clean" as an absolute should read this paragraph first.

### 3.2 The scrub is per-call-site, so it can rot

Nothing structurally prevents a future `console.log` from interpolating a name; the tests cover the
call sites that exist. A lint rule (ban bare template interpolation of known content fields into
`console.*`) would make it structural. Not built in stage 1; noted as the honest limit of what a
call-site scrub buys.

## 4. THE FINDING: `Event` still carries user content, because R2 keys are name-derived

The banked question for this statement was: **are project and film ids name-derived?** Checked, not
assumed, and the answer has two halves that point in opposite directions.

**The ids are NOT name-derived.** `storyboard_projects`, `cast_members` and `renders` all expose a
`public_id` that is a canonical **UUID v4** from the platform CSPRNG (`vivijure-core/public-id.ts`,
security finding F13). Every `:id` route accepts only that shape. So
`/api/storyboard/projects/<uuid>` is opaque, and the `?project_id=` filter is opaque.

**The R2 KEY NAMESPACE is name-derived, and it is in the URL.** The render path does not use the
public id:

- the bundle key is `bundles/<projectName>-<contentHash>.tar.gz`;
- the film job's `project` field is DERIVED FROM THAT KEY (`deriveProjectFromBundleKey`);
- render outputs are written to `renders/<project>/clips/<shot_id>...`;
- and the studio serves artifacts at **`/api/artifact/*key`**, whose pathname IS that R2 key.

So a tenant fetching their own render produces a request URL containing the project name they chose.
`Event` is a single opaque object with no field selection, so there is no way to take timing or
status without taking the URL.

**Consequence for the stage-2 ruling, in the direction that matters:** the shorthand "opaque ids plus
timing" is **wrong for `Event`**, and wrong in the understating direction. If observability were
enabled today, post-scrub, the ingested dataset would include **project names, as slugs, inside
request URLs**. A project name is exactly the kind of thing a customer would not expect to hand over
("my-divorce-film", a client name, an unreleased title).

**This is a second scrub target, not a stage-2 caveat.** Making the artifact route address objects by
public id (or by an opaque per-object handle) would remove the name from the URL and make "opaque ids
plus timing" TRUE rather than approximately true. It is a bigger change than stage 1 -- key scheme,
stored keys, backend contract, and both panels in parity -- so it is filed as a finding here rather
than smuggled into this PR.

## 5. Summary for the ruling

| Question | Answer |
|---|---|
| Are the studio's own log lines content-free after stage 1? | **Yes at every call site it authors**, with the enumerated second-order residual in 3.1. |
| Would `Logs` be safe to ingest? | Materially safer than the audit found. Not provably zero (3.1). |
| Would `Exceptions` be safe to ingest? | The one named leak is closed; same residual, plus stack traces carry file and function names (ours, not the user's). |
| Would `Event` be safe to ingest? | **No.** It carries the request URL, and the URL carries the project NAME via the R2 key namespace (section 4). Unchanged by stage 1 and not fixable by a log scrub. |
| Does stage 1 change the 2026-07-19 posture? | **No.** Nothing is enabled. The synthetic-check route (cf#115 option B) remains the way to watch tenant liveness without touching customer content, and it is not blocked on any of this. |
